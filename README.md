# HearAble — Smart Emergency Alert App for Deaf and Hard-of-Hearing People

HearAble listens for dangerous and important sounds **on the phone**, turns them into
**visual and vibration alerts**, and — if the user asks for help or does not respond to a
possible emergency — **sends an SMS to their emergency contacts**.

> ⚠️ HearAble is a support tool. It **cannot guarantee** that every sound is detected or
> that every message is delivered. It must not be the user's only safety measure.

---

## 1. Features

| Area | What HearAble does |
|---|---|
| **Accounts** | Sign up (name, email, phone, emergency contacts, optional guard house), email verification, login, forgot password, auto-login, log out |
| **Consent** | Permissions screen explaining every permission; privacy consent (versioned); emergency-contact consent |
| **Sound detection** | Google **YAMNet** (TensorFlow Lite) running **on the device**. Audio is analysed in ~1 s windows every 0.5 s and **never saved or uploaded** |
| **Tier 2 – emergency** | Smoke/fire alarm (3 of last 4 frames ≈ 2 s) and glass breaking (one strong frame) → full-screen "Are you safe?" with **30 s countdown** |
| **Loud-bang check-in** | Bang, slam, thump, smash, boom, clatter → **60 s countdown** with *I'm safe / I need help / Ignore* (reason + mute 1/5/10 min) |
| **Tier 1 – alert only** | Vehicle horn, siren, doorbell, knocking, baby crying, screaming, car alarm → visual + vibration + flashlight, **never contacts anyone** |
| **Escalation** | Unique event ID, loud local siren, **automatic SMS from the phone's SIM** (Android) with real *sent / delivered / failed* status per contact, retry, "I'm safe" follow-up SMS, call buttons |
| **Safeguards** | Duplicate cooldowns, 2-min suppression after "I'm safe", loud-bang mute never mutes smoke/glass, rate limit (3 emergency rounds / 30 min), one SMS round per event, simulated alerts never send |
| **Background (Android)** | Foreground service (type *microphone*) with permanent notification; heads-up alerts; full-screen emergency alerts over the lock screen; honest "monitoring stopped" notifications |
| **History** | All alerts with filters (type, date range), per-contact delivery details, false-alarm reasons, delete one / delete all |
| **Settings** | Sound categories (smoke/glass locked on), sensitivity, vibration, flashlight, siren, countdowns within safe limits |
| **Profile & privacy** | Edit name/phone, change password, in-app privacy policy, **delete account and all data** |
| **Test mode** | Simulate any sound; clearly labelled **SIMULATED** everywhere and saved as a test |
| **Accessibility** | Large text and touch targets (≥ 48 px, main buttons 60–80 px), high contrast, screen-reader labels and live regions, no audio-only warnings, slow pulse (< 3 flashes/s) |

## 2. Technology

| Purpose | Technology |
|---|---|
| App | Flutter / Dart |
| Login | Firebase Authentication (email + password) |
| Database | Cloud Firestore (region `asia-southeast1`, Singapore) |
| Sound model | YAMNet (TensorFlow Lite) via `tflite_flutter` |
| Microphone | `record` (16 kHz mono PCM stream) |
| SMS | Native Android `SmsManager` (Kotlin, `hearable/sms` channel) |
| Background | Native Android foreground service (Kotlin, `hearable/background` channel) |
| Alerts | `vibration`, `torch_light`, `audioplayers` (generated siren), `url_launcher` (call / SMS apps) |
| Permissions | `permission_handler` |

## 4. Database structure (Cloud Firestore)

```
users/{uid}
  fullName, email, phone, language
  contactConsentConfirmed, contactConsentAt, createdAt, updatedAt
  privacyConsentVersion, privacyConsentAt
  settings { enabledCategories[], vibration, flashlight, localAlarm,
             sensitivity, emergencyCountdown, checkInCountdown }

users/{uid}/contacts/{contactId}
  name, phone (+60…), role (primary | secondary | guardHouse)
  lastTestStatus, lastTestAt, consentConfirmed, createdAt, updatedAt

users/{uid}/events/{eventId}          ← eventId is the unique emergency event ID
  categoryKey, category, tier (emergency | checkIn | alertOnly)
  score, simulated, detectedAt, createdAt, updatedAt, outcome
  userResponse (safe | need_help | ignored), respondedAt
  ignoreReason, muteMinutes
  escalated, escalationReason, escalatedAt, escalationStatus
  cancelledByUser, cancelledAt, allClearSent
  notifications { contactId: { name, phone, role, status, error, updatedAt } }
```

Security rules are in **`firestore.rules`**. Each user can only access their own data; fields,
phone format and contact roles are validated; event type, time and the `simulated` flag
cannot be changed after creation.

## 5. Setup (Windows, Android)

### 5.1 Tools
1. Install **Flutter** (stable) and **Android Studio** (Android SDK, SDK Command-line Tools, an emulator).
2. Install **Git** and **Node.js LTS**.
3. VS Code with the **Flutter** extension.
4. `flutter doctor` — all green.

### 5.2 Firebase
1. Create a Firebase project. Enable **Authentication → Email/Password**.
2. Create **Firestore** (production mode, `asia-southeast1`).
3. Publish the rules from `firestore.rules` (Firestore → Rules).
4. Install the CLIs and link the app:
   ```powershell
   npm install -g firebase-tools
   firebase login
   dart pub global activate flutterfire_cli
   flutterfire configure --project=<your-project-id> --platforms=android
   ```
   (Add `%LOCALAPPDATA%\Pub\Cache\bin` to PATH. If PowerShell blocks scripts:
   `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.)

### 5.3 Sound model
```powershell
Invoke-WebRequest -Uri "https://storage.googleapis.com/mediapipe-models/audio_classifier/yamnet/float32/latest/yamnet.tflite" -OutFile "assets\models\yamnet.tflite"
Invoke-WebRequest -Uri "https://raw.githubusercontent.com/tensorflow/models/master/research/audioset/yamnet/yamnet_class_map.csv" -OutFile "assets\models\yamnet_class_map.csv"
```

### 5.4 Android build notes
- `android/app/build.gradle.kts`: `compileSdk = 37` (required by `permission_handler`).
- `android/gradle.properties`: `android.suppressUnsupportedCompileSdk=37`.
- `android/build.gradle.kts`: Kotlin JVM-target fix for plugins that compile Java 11
  (`tflite_flutter`, and any other plugin named in an "Inconsistent JVM Target" error).
- `AndroidManifest.xml` declares: `RECORD_AUDIO`, `POST_NOTIFICATIONS`, `VIBRATE`, `SEND_SMS`,
  `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE`, `USE_FULL_SCREEN_INTENT`,
  `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, the `MonitoringService`, and a `tel:` query.

### 5.5 Run on a physical device
1. Phone: Settings → About phone → tap **Build number** 7×; Developer options → **USB debugging** on.
2. Connect by USB, accept the prompt.
3. `flutter devices` → `flutter run -d <device-id>`.
4. In the app's dashboard, make every status row green (microphone, notifications, SMS,
   battery optimisation, full-screen alerts).
5. Xiaomi / Oppo / Vivo / Huawei: also enable **Autostart**, battery **No restrictions**,
   and lock the app in recent apps.

> The emulator cannot send SMS and has no vibration/flashlight. Use a real phone for alerts.

## 7. Building the Android app

### 7.1 APK for testers (sideload)
```powershell
flutter build apk --release --split-per-abi
```
Share `build\app\outputs\flutter-apk\app-arm64-v8a-release.apk`
(or `flutter build apk --release` for one universal `app-release.apk`).
Testers must allow "Install unknown apps". Increase `version:` in `pubspec.yaml`
(e.g. `1.0.1+2`) for every new build.

### 7.2 Release signing (needed for an AAB / Play Store)
1. Create a key (keep it and its passwords safe — losing it means you can never update the app):
   ```powershell
   keytool -genkey -v -keystore $env:USERPROFILE\hearable-upload.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload
   ```
2. Create `android/key.properties` (**never commit this file**):
   ```properties
   storePassword=<password>
   keyPassword=<password>
   keyAlias=upload
   storeFile=C:\\Users\\<you>\\hearable-upload.jks
   ```
3. In `android/app/build.gradle.kts`, load `key.properties`, add a `release` signing config,
   and use it in `buildTypes.release` (see Flutter docs: *Build and release an Android app*).
4. Build:
   ```powershell
   flutter build appbundle --release
   ```
   Output: `build\app\outputs\bundle\release\app-release.aab`.

> **Play Store note:** Google Play restricts the `SEND_SMS` permission. Publishing would require
> Google's approval for this use, or switching to the server-based SMS option (section 10).
> Sideloaded APKs and Firebase App Distribution are not affected.

## 8. iOS (requires a Mac)

1. On a Mac with **Xcode** and CocoaPods: `flutterfire configure --project=<id> --platforms=android,ios`.
2. `ios/Runner/Info.plist` already contains `NSMicrophoneUsageDescription`.
3. In `ios/Podfile`, inside `post_install`, enable only the permissions HearAble uses:
   ```ruby
   target.build_configurations.each do |config|
     config.build_settings['GCC_PREPROCESSOR_DEFINITIONS'] ||= [
       '$(inherited)',
       'PERMISSION_MICROPHONE=1',
       'PERMISSION_NOTIFICATIONS=1',
     ]
   end
   ```
4. `cd ios && pod install`, open `ios/Runner.xcworkspace` in Xcode, set your **Team** and a
   unique **Bundle Identifier** under *Signing & Capabilities*.
5. Run on an iPhone from Xcode or `flutter run`.
6. Distribute: Apple Developer Program → Xcode **Product → Archive** → upload to
   **App Store Connect** → **TestFlight**.

**Honest iOS limitations:** Apple does not allow apps to send SMS automatically — HearAble opens
Messages with the alert pre-written and the user taps Send. Background monitoring is not yet
implemented on iOS; monitoring stops (and says so) when the app leaves the screen.

## 9. Known limitations

- Detection may fail if the phone is far away, covered, in a pocket, muted microphone, or noisy surroundings.
- YAMNet scores are estimates, not probabilities; thresholds are starting values and need tuning
  with more real recordings.
- Monitoring stops if the app is swiped away or the phone restarts (the user is notified).
- SMS depends on the user's signal and credit; some networks never confirm delivery
  (shown as "delivery not confirmed").
- Client-side idempotency and rate limits protect against duplicates within the app; a server
  backend would add server-side guarantees.
